## 1. Security — fix first

**1.1 The auth rate limit does not limit anything.**
`GameServer.guard` (`server/gameServer.js:~215`) keys the limiter on
`` `${socket.handshake.address}:${socket.id}:${action}` ``. Two problems compound:

- `socket.id` is in the key, so a client that opens a fresh socket gets a fresh budget.
  The "5 logins per 5 minutes" on `login` is bypassed by reconnecting.
- `app.set("trust proxy", ...)` is never called and Render terminates TLS at a proxy, so
  `handshake.address` is the same value for every real client anyway.

Fix: key auth-sensitive actions (`login`, `register`, `resumeSession`) on the *client* IP
taken from the forwarded header (configure Express/Socket.IO to trust the platform proxy
first — do not read `X-Forwarded-For` raw), and drop `socket.id` from those keys. Keep
`socket.id` for per-connection gameplay spam limits where it is correct. Add a failed-login
counter per account, not only per IP.

**1.2 `login` leaks which emails are registered by timing.**
`server/authService.js` throws immediately when `findAccountForLogin` returns null, so a
miss returns in a few ms while a hit pays a bcrypt round (cost 12, ~250 ms). Compare against
a dummy hash on the miss path so both branches cost the same.

**1.3 Database TLS is not verified.**
`database/database.js` sets `ssl: { rejectUnauthorized: false }` whenever `DATABASE_SSL`
isn't the string `"false"`. That accepts any certificate, including an attacker's. Supply the
provider CA (Neon/Render publish one) and verify, or at minimum make the insecure mode an
explicit opt-in variable that production refuses.

**1.4 Owner privilege is claimed by display name.**
`database/ownerProvisioning.js` promotes whichever account has the display name `"orbit op"`
to `role = 'owner'`. Anyone who registers that name first becomes owner. Key it on the
owner's email (or an account id in an env var) instead. Also move the `ALTER TABLE
accounts DROP CONSTRAINT / ADD CONSTRAINT` out of the boot path and into `schema.sql` — DDL
should not run on every restart.

**1.5 `role`, `bans` and `mutes` are decoration.**
Nothing reads `accounts.role`, and the `bans`/`mutes` tables are never queried. A banned
account signs in and plays normally; only `account_status` is checked. Either enforce them on
login and on `joinRoom`/`chatMessage`, or delete the tables and the column so the schema stops
implying a moderation system that does not exist.

**1.6 `/tips` CSP allows `unsafe-eval` and a CDN.**
`server.js` widens the policy for the embedded game to include `'unsafe-eval'` and
`https://cdn.jsdelivr.net` in both `script-src` and `connect-src`. Confirm the embedded game
genuinely still needs both (it may have been for a since-removed loader). If it does, keep
them; if not, drop them. This is the widest policy in the app and it is the route with the
weakest authentication.

## 2. Correctness — gameplay bugs

**2.1 Vent state leaks between matches.** `room.sealedVents` and `room.minedVents` are created
lazily in `server/roleEngine.js` (Plumber `sealNearestVent`, Miner `digVent`) and are never
cleared in `createRoom`, `startMatch` or `resetRoomToLobby`. A vent a Plumber welded in match
one is still welded in match two, and mined vents accumulate forever. Initialise both in
`createRoom` and reset them in `startMatch` and `resetRoomToLobby`.

**2.2 Mined vents cannot be entered or hopped to.** `enterVent` and `moveVent`
(`server/gameServer.js:~1624` and `:~1646`) resolve vents with `stationById(room.mapId, …)`,
which only searches the authored map. `publicVentState` and `ventsInNetwork` *do* include
`room.minedVents`. So the Miner digs a vent, it is listed as an exit, and every attempt to use
it fails with "Vent not found." Route both through one resolver that unions authored and mined
vents.

**2.3 A sealed vent can still be hopped to.** `enterVent` checks `room.sealedVents`; `moveVent`
does not. A player already inside the network can hop to a welded vent. Apply the same check
in `moveVent`.

**2.4 The client picks elimination targets the server will refuse.** `tryEliminate` in
`public/src/game.js:~605` hardcodes `let best = 3.2;` while the server checks
`room.settings.eliminationRange` (default 2.35, host-settable 1.5–3.0). At default settings the
client happily selects a target 3.0 units away and the server answers "Target is out of range."
Use `this.room.settings.eliminationRange`.

**2.5 Three separate copies of the same two constants.** `INTERACTION_RANGE` (2.8) is declared
in `server/gameServer.js` and `public/src/game.js`; `ROLE_TARGET_RANGE` (3.2) in
`server/gameServer.js`, `public/src/game.js` and `server/roleEngine.js`. 2.4 is exactly the
failure mode this invites. Move both into a shared module (alongside `movementPhysics.js`) and
import them everywhere.

**2.6 The task modal is shared by two owners that fight over it.**
`TaskInterface` and `RepairInterface` both bind `#task-modal`, `#task-challenge` and
`#task-cancel`. `TaskInterface`'s cancel handler calls `this.close()` unconditionally — it does
not check `this.active` the way `RepairInterface`'s does — so dismissing a repair panel also
tears down the task stage. Neither `open()` refuses when the other owns the modal. Give the
modal a single owner (a small controller both defer to), or at minimum guard both cancel
handlers and both `open()` calls.

**2.7 `radio` repair short-circuits multi-station outages.** In `repairAction`
(`server/gameServer.js:~1215`) the `keypad` branch sets
`solved = sabotage.repairStations.every(id => sabotage.repairs.has(id))` but the `radio`
branch sets `solved = true` outright. It is correct today only because
`skeld-comms-sabotage` happens to have one station. Make it check `every` like the keypad, so
a future two-dial sabotage doesn't silently become a one-dial one.

**2.8 The breaker shuffle is biased.** `makeRepairPanel` uses
`[0,1,2,3,4].sort(() => Math.random() - 0.5)`, which is not a uniform shuffle — some breaker
combinations come up far more often than others. There is a correct Fisher–Yates `shuffle()`
in the same file, twenty lines up. Use it.

**2.9 Matches are recorded against the wrong map.** `database/repositories/statsRepository.js`
inserts `map_id` as the literal `'osv-meridian'` instead of `room.mapId`. Every match row is
wrong. Pass the real id through `endMatch`'s payload.

**2.10 The host's operative count is silently overridden.** `startMatch` computes
`Math.min(settings.operativeCount, Math.max(1, Math.floor(activePlayers.length / 4)), …)`.
A host who sets 3 operatives in a 10-player lobby gets 2, with no feedback. Either honour the
setting up to `players - 1`, or clamp `operativeCount` in the lobby UI so the number shown is
the number that will happen.

**2.11 The sample-analyser timer survives the match.** `SAMPLE_TIMERS` in
`public/src/tasks/minigames.js` is a module-level `Map` keyed on `taskId:site` and is only
deleted on success. Start the analyser, die, return to lobby, start a new match — the same
task id is already "analysed". Clear it on match end/reset.

**2.12 Corrupt localStorage crashes the boot path.** `restoreIdentity`, `resumeRoom` and
`defaultAppearance` all call `JSON.parse(localStorage.getItem(…))`; only `defaultAppearance`
wraps it in `try`. A malformed value throws out of the "continue" click handler and the player
sees nothing happen. Wrap the other two, or add one `readStored(key)` helper that all three use.

**2.13 Role hook failures are invisible.** `fireHook` in `server/roleEngine.js` catches and
discards every exception with a bare `catch {}`. A role whose hook throws every match is
undetectable. Log it (role id + hook name + message) while still not breaking the match.

**2.14 `exitVent` does not check phase or liveness.** Every other vent handler gates on
`room.phase === PHASES.ACTIVE && player.alive`; `exitVent` gates on neither. Add them for
consistency.

## 3. Gameplay completeness

**3.1 The Doors sabotage is missing.** `public/src/maps/theSkeld.js` defines four sabotages —
reactor, O2, comms, lights. The real Skeld has five; door sabotage (seal a room's doors for a
short timer, no repair station) is the one operatives use most and it is absent entirely. It
needs: a sabotage definition with no repair stations, a door-state model on the room, movement
blocking at the door line, a client render, and an expiry. This is the largest single gap
between this game and its reference.

**3.2 Sabotage identity is sniffed from strings.** `lightsAreOut` runs
`/lights|lighting/u.test(activeSabotage.id)` and `requestSecurity` runs
`activeSabotage.id.includes("comms")`. Rename a sabotage id and the lights stop going out.
Put `blindsPlayers` / `jamsTelemetry` flags on the sabotage definition and read those.

**3.3 "Clean Vent" is not a Skeld task.** It exists in `theSkeld.js` as
`skeld-clean-vent`. It belongs to other maps in the reference. Either drop it or note in the
file that it is a deliberate addition.

**3.4 Only one map ships.** `MAP_IDS` is `["the-skeld"]`, so the map selector has a single
option. That is fine as a state of the world, but the README (see 5.1) claims three.

## 4. Performance and structure

**4.1 `stationById` is a linear scan on every interaction.** It runs
`getMapDefinition(mapId).stations.find(...)` over ~60 stations, and is called several times per
task/repair/vent action; the client's `nearestInteractable` walks the same list every frame.
Build a per-map `Map` index once at `createMapDefinition` time and look up by key.

**4.2 `snapshotPlayer` is O(n²) per snapshot.** For each player it runs
`[...room.players.values()].some(...)` to find a medic shield — 20 times a second, for every
player, in every room. Compute the shielded-player set once per snapshot tick and pass it in.

**4.3 `survivorWinnerIds(room)` is recomputed inside the per-player map in `endMatch`.** Hoist
it out of the loop.

**4.4 Critical-sabotage rebroadcast uses modulo timing.** `now % 1000 < 1000 / TICK_RATE` in
`tick()` is a fragile way to say "about once a second" — it double-fires or skips depending on
tick drift. Track a `lastCriticalBroadcastAt` timestamp instead.

**4.5 `recordMatch` issues 2N round trips.** One `INSERT` and one `UPDATE` per player,
sequentially awaited inside the transaction. Batch the `match_players` insert into a single
multi-row statement and the stats updates into one `UPDATE … FROM (VALUES …)`.

**4.6 `match_players` is keyed on `(match_id, display_name_snapshot)`.** It works only because
duplicate display names are rejected at join time. That is a load-bearing coincidence in a
different layer. Use a surrogate key or `(match_id, account_id)` with a slot index for guests.

**4.7 `schema.sql` has no migration story.** It is all `CREATE TABLE IF NOT EXISTS`, so adding
a *column* to an existing table does nothing on an already-migrated database — which is
presumably why the role-constraint DDL ended up in `ownerProvisioning.js`. Introduce numbered
migration files and a `schema_migrations` table.

## 4a. The O2 keypad code is broadcast to the whole room

`publicRepairPanel` returns `code: panel.code`, and `repairAction` broadcasts the panel to
`io.to(room.code)` on every interaction. The comment says the code is "written on the sticky
note beside it", but in practice every player in the match receives it the moment anyone
touches either keypad, without walking to O2. Proximity is still enforced for the *fix*, so
this is a flavour bug rather than an exploit — but if the sticky note is meant to be
information you have to go and read, only send `code` to sockets within reach of a keypad.

## 5. Documentation and build hygiene

**5.1 The README describes a different game.** `README.md` currently claims:
- "one of three isolated maps: **The Skeld**, **MIRA HQ**, or **Polus**" — only the Skeld exists
- "10 Hz world snapshots" — `SNAPSHOT_RATE` is 20
- "Eight map-specific server-sequenced assignments per map" and "the reference's nine
  assignments" — there are 19 tasks across 29 consoles
- "Four map-specific sabotage systems per map" — there are four total, on one map

Rewrite it against the code as it is. This is the first thing anyone reads.

**5.2 Two package managers.** `pnpm-lock.yaml` is committed but `render.yaml`'s build command
and the README both run `npm install`, so the lock file is ignored and deploys are not
reproducible. Pick one — if pnpm, change the build command to `pnpm install --frozen-lockfile`;
if npm, delete the pnpm lock and commit `package-lock.json`.

**5.3 `npm run check` covers about half the source.** The `check` script names 24 files by
hand. It does not include `netClock.js`, `callsign.js`, `tasks.js`, `tasks/minigames.js`,
`repairInterface.js`, `sabotage/repairPanels.js`, `network.js`, `input.js`, `settings.js`,
`audio.js`, `assetLoader.js`, `assetManifest.js`, `artCatalog.js`, `game2d/assets.js`,
`game2d/VentArrows.js`, `game2d/VisionOverlay.js`, `game2d/TrackerArrow.js`,
`maps/theSkeld.js`, `maps/skeldWalkGrid.js`, `server/validation.js`, `server/authService.js`,
`server/rateLimits.js`, `server/constants.js`, or anything under `database/`. Replace the hand
list with a glob so new files are covered automatically.

**5.4 Cross-server deployment is still half-configured.** Not a code change — the code is
ready. On Railway, `CROSS_SERVER_PUBLIC_URL` must point at Railway's own domain (it currently
points at Orbit Ops, which is self-advertisement); on Render it must be set at all
(`https://orbit-ops.onrender.com/tips` is now valid since the gateway admits a handoff there).
Render's `JIMS_DATABASE_URL` must equal Railway's `DATABASE_URL` or the shared room directory
is two separate directories. `CROSS_SERVER_ORBIT_URL`, `CROSS_SERVER_INVITE_SECRET` and
`SERVE_WEB_CLIENT` on Railway are read by nothing and can be deleted.

**5.5 Room codes are only unique within one server.** `createRoom` does
`while (this.rooms.has(code))` — a purely local check. With two deployments sharing a room
directory, two rooms can hold the same 5-character code and a cross-server join goes to the
wrong one. Check the candidate code against the shared `active_game_rooms` table before
claiming it.
